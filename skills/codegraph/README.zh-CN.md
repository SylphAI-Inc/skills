# codegraph

**把任意代码库变成一张可以点来点去探索的交互图 —— 最终就是一个自包含的 HTML 文件。**

一次确定性扫描会提取出文件、import 关系、符号、调用边、PageRank 重要性排名、架构层级、循环依赖和入口点。剩下"这是什么意思"的部分交给你来补充 —— 用通俗易懂的摘要和导览把它讲清楚。最终产出是一个离线的 HTML 文件，里面有三个联动的视图：架构**总览图**、可以拖着转的**星图**，还有可以逐层展开的**探索树**。

不需要构建步骤，不依赖 CDN，产物里也没有塞任何 API key。**只需要 `python3` 3.8+**（纯标准库）。230k 行代码大概 2 秒就扫完。

## 三个视图

你拿到的是一个 HTML 文件，里面装着同一次扫描的三个联动视图，用 `Tab` 键来回切换。点击总览图里的模块方块，或者星图里的某个星系，都会跳转到探索视图并聚焦到那个模块的文件上。

| 视图 | 回答的问题 | 是什么 |
|---|---|---|
| **overview（总览）** | *"这个系统由哪些部分组成？"* | 架构图 —— 模块方块按层级带排列，连接线上有流动的光点，主依赖路径上还带个彗星特效。这张图是从扫描结果直接算出来的，不是人画的，所以永远不会跟真实代码脱节。 |
| **star map（星图）** | *"这个系统的重心在哪？"* | 把同样的模块画成一个可以拖着转的星系，亮度代表重要性。拖拽转视角，滚轮缩放，Shift+拖拽平移，按 `0` 复位。用 Canvas 画的 2.5D 效果 —— 没用 three.js，也没用 WebGL。 |
| **explore（探索）** | *"这些模块是怎么连起来的？"* | 一棵逐层展开的树：文件夹 → 文件 → 符号，一次只展开一层。每个折叠的节点上都有个 `+N` 徽章告诉你里面还有多少东西，不会有内容被悄悄藏起来。 |

![codegraph star map — AdalFlow](./assets/codegraph-adalflow-starmap.png)

<sub>同样是 AdalFlow 这次扫描出来的星图 —— 每个模块都是一个星系，亮度和星团大小都跟重要性挂钩。`core` 和 `components/model_client` 位于整张依赖网的中心，`optim` 和 `tracing` 各自形成了独立的分支。</sub>

### 每个节点都有话可说，而且零模型调用

`scan.py` 会去读代码库**自己写的 docstring 和文件头注释** —— 模块的 docstring、JSDoc 块、Go/Rust 里的行注释 —— 直接拿来当节点摘要用。样板文字会被过滤掉，摘要在 `Args:`/`Returns:` 处截断，保证一句话搞定。

在一个真实的 10.9 万行代码仓库上测过：**87% 的文件在零模型调用的情况下就已经有摘要了。** Agent 写的 `enrich.json` 可以在能说得更好的地方覆盖这些摘要，检查器也会标出来哪个摘要是哪来的 —— 提取出来的摘要会标注"来自文件自身的 docstring"，来源永远不会含糊。

这一点很重要，因为一堆没有标签的点堆在一起是教不会任何人东西的。

### 让密集的仓库依然可读

真实的仓库很容易画出一团乱麻，所以探索视图**默认是简化过的**，读者可以自己再把细节加回来：测试文件默认隐藏，hub 文件（枢纽文件）的边默认折叠成一个 `⋯n` 徽章，`calls` 边默认关闭（因为它的数量通常是 import 的 5 倍左右），还有基于距离的细节层级和邻域聚焦模式。

在一个 10.9 万行代码的仓库上测过：默认设置下边数从 **628 降到 172（-73%）**，聚焦模式下能再降 **-87%**。

**为什么不做成 3D？** 因为真正的乱源是边的*数量*，不是缺了一个维度。3D 只会带来遮挡、旋转导致的迷失方向感，还要多引入约 600KB 的 three.js —— 这会破坏"单文件离线"这个契约。用细节层级加折叠反而才是真正解决问题的办法。

## 为什么要做这个东西

接手一个陌生仓库基本就是在"考古"：grep 一下，跟着一个 import 追进去，追到一半断了线索，只能从头再来。常规工具帮不上太多忙 —— `tree` 只能看到文件夹，看不出数据流向；IDE 的调用图只有边，看不出哪个更重要；自动生成的依赖图放到真实项目里基本就是一团乱麻，没人会看第二眼。

codegraph 把这个问题按它本该被拆分的方式拆开了：

- **脚本负责结构** —— 文件、import、调用、各种指标、循环依赖、层级。确定性、可复现：同一个 commit 永远得到同样的边。
- **模型负责语义** —— 一个文件是*干什么用的*，以及该按什么顺序去读。这个只有模型才写得出来。

**这个工具的目标不是画一张炫技的复杂图 —— 而是画一张能悄悄教会别人这些部件是怎么拼起来的图。** 正因为这样，最有价值的产出其实根本不是那张图，而是导览（tour），因为"该按什么顺序读"才是新人真正缺的东西。

## 什么时候该用它

当有人需要**理解一整个仓库**，而不是一个文件的时候，用 codegraph：

- "帮我理解一下这个代码库" / "我刚加入这个项目"
- "画/可视化/图解一下这个仓库或它的架构"
- "入口点在哪？" / "我该从哪开始读？"
- "数据是怎么在这里面流动的？" / "生成一份上手指南"
- "给我看看依赖图" / "找找有没有循环依赖"
- "这里面哪些文件最重要？"

**不要**拿它来解释单个文件 —— 那种情况直接读文件就行。

## 它是怎么实现的

三个阶段。其中两个是确定性的，只有中间那一步用到了模型。这个拆分本身就是设计的核心 —— 结构永远不依赖模型的猜测，语义也从不假装自己是可复现的。

```
1. scan.py    代码库    ──▶  graph.json + digest.md    确定性，无 LLM，无网络
2. Agent      digest.md ──▶  enrich.json                摘要、层级修正、导览
3. render.py  两者合并  ──▶  codegraph.html             一个便携的自包含文件
              （overview.py 会顺路把图压缩成总览图）
```

| 阶段 | 负责人 | 保证什么 |
|---|---|---|
| 结构（文件、import、调用、指标、循环依赖） | `scan.py` | 可复现 —— 同一个 commit，同样的边 |
| 语义（一个文件是干什么的、导览路线） | Agent | 只有模型才写得出这个 |
| 交付（排版、校验、生成 HTML） | `render.py` | 写文件前先校验；坏产物永远不会替换掉一个好的产物 |

`graph.json` 是机器生成的产物，永远不会手写；Agent 只会去写 `enrich.json`。因为这两个是分开的文件，**重新扫描不会丢掉已有的摘要** —— 只有已经不存在的 id 才会被清理掉。

## 交互操作参考

| 按键 | 作用 |
|---|---|
| `Tab` | 在总览图和探索树之间切换 |
| `/` | 按名字、路径、摘要文本或标签搜索 |
| `P` · `[` · `]` | 播放 / 单步执行导览 |
| `F` | `simplify` —— 折叠 hub 文件的边（大概能减少 -48% 的杂乱） |
| `N` | `focus` —— 只显示当前选中节点加上它的主要邻居（大概能减少 -87%） |
| `H` | 切回扁平的全量图 |
| `space` | 暂停动画（截图的时候用得上） |
| `T` · `0` | 切换主题 · 适配窗口/复位视角 |

每个节点还带着一个 **`ask ▸`** 按钮，一键复制一份完整的 prompt —— 路径、摘要、代码行数、入度/出度、定义的符号、双向依赖关系全都打包好，直接粘贴到任意 LLM 里就能问。故意**没有做**的一件事：在 HTML 里塞 API key。因为这个文件会被提交和分享出去，塞了密钥进去就是等着被泄露的定时炸弹。

## 诚实说明局限性

提取方式是基于正则表达式的，不是完整的类型检查 AST —— 对 import 和定义提取效果很好，但调用关系只是近似估计。

- **`calls` 边只是个提示，不是事实。** 只匹配唯一无歧义的名字；`get`/`run` 这类常见名字会被故意跳过。Import 关系是可信的。
- **动态 import、依赖注入容器、反射、运行时注册**，静态扫描全都看不见。
- **层级(layer)只是路径启发式猜测**，除非 Agent 在 `enrich.json` 里手动覆盖它。
- 生成代码、压缩后的 bundle、lockfile 会被故意排除在外。

## 输出产物的约定

一个自包含的 `.html` 文件，路径在 `<repo>/.codegraph/codegraph.html`：

- 内联的 CSS/JS 和内联 SVG，**没有 CDN，没有外部资源，也没有 API key**
- 离线可用，直接从文件系统打开就行 —— 可以放心提交或用邮件发出去
- 按 `space` 可以暂停动画，系统开启"减少动画"偏好时会自动关闭
- 性能跟图的大小是解耦的：静态场景画在一个底层 canvas 上，动画放在另一个 overlay 上，粒子数量有上限。实测**在一个 2,660 个节点的图上能跑到 60fps**

把 `.codegraph/` 提交进仓库，团队成员打开就能直接看图，零配置。
